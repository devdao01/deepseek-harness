# Agent Note: Per-user ticket identity and per-session access control

Status: implemented

English | [中文](2026-08-21-per-user-ticket-and-session-access.zh.md)

## Problem

[Bearer-token authentication](2026-08-21-api-bearer-token-authentication.md) added ONE credential: a full token that grants unscoped access. The decided deployment puts Odoo in front of the harness for 1000+ concurrent users with real streaming — Odoo does auth and management, but the browser talks DIRECTLY to the harness for runtime (unary + SSE/WS streams), because relaying 1000+ streams through Odoo does not scale. So the harness itself must resolve *which user* a runtime request belongs to and filter per user, in the Node stream. The full token cannot do this: it is one shared credential with no identity, and handing it to every browser would give every user total access. The user decided to add a SECOND credential kind — a short-lived per-user signed ticket — plus a per-session access list the harness enforces, so a browser carrying a ticket sees and acts on only the sessions its user was granted.

## Decision

Three layers, each independently testable, layered above the existing reachability fence and bearer-token auth without changing either for non-ticket deployments.

**1. Per-user ticket ([`@deepseek-ai/dsh-user-ticket`](../../../packages/identity/user-ticket/src/index.ts)).** A compact HMAC-SHA256 credential the harness VERIFIES but never mints (Odoo mints and refreshes). Format `v1.<b64url(payload)>.<b64url(mac)>`, `payload = {u,exp}`, MAC over the ASCII `"v1." + body`. `verifyTicket` checks authenticity first (constant-time `timingSafeEqual` over equal-length digests), then a max-TTL guard, then expiry with clock-skew tolerance; it returns `{ok,userId} | {ok:false, reason:'expired'|'invalid'}`. `ApiPrincipal = {kind:'token'} | {kind:'ticket',userId}` is the resolved identity threaded through dispatch. `auth.ticket` config carries the shared `secret` (fail-loud below 32 chars; empty ⇒ disabled), `maxTtlSeconds` (default 900), and `clockSkewSeconds` (default 30). In [`api-auth`](../../../packages/client/connection/src/api-auth.ts), `authenticateApiRequest` now returns `{status:'ok',principal} | {status:'absent'} | {status:'invalid',reason}`: a full token is tried first (unchanged, `{kind:'token'}`), else the ticket verifier resolves a per-user principal or a reason. An expired/invalid ticket is a transport **401** carrying `WWW-Authenticate: Bearer error="invalid_token"...` (`ticketChallenge`) so the SPA re-mints through Odoo; an unknown full token stays header-less 401 as before. Ticket principals never unlock the `auth.unpinned` privileged methods.

**2. Per-session access list ([`@deepseek-ai/dsh-session-access`](../../../packages/session/session-access/src/index.ts)).** A capability seam (Definition + single durable Provider; Consumer is the API proxy). `SessionAccessService` opens its own `session_access` storage domain (one `access` table keyed by session id), NOT the session log. `get` returns the allowed-user set (empty for an unknown session), `set` replaces it (empty ⇒ delete the row), `canRead(principal, sessionId)` is the single fail-closed gate (full token always; ticket iff an explicit member), and `onChanged` fires after each durable write. Every change lands as a `domain/changed` event and the current set is reconstructed by reopening the domain — the projection posture, in the domain-store plane.

**3. Filter and enforce by userId.** The fence resolves the principal once ([`resolveHttpPrincipal`](../../../packages/client/connection/src/api-auth.ts)) and threads it into `toFetchHandler(apiProxy, principal)` and the WS downlink stream openers. A third principal kind — **`anonymous`** — closes the absent-credential hole: behind nginx the browser reaches the harness from 127.0.0.1 carrying a trusted `Host`, so the reachability lane would otherwise grant a credential-less request full access and let a user bypass the ACL by omitting the ticket. `resolveHttpPrincipal` returns `token` (full) for a credential-less request ONLY when ticket auth is off (byte-for-byte the pre-ticket behavior); once `auth.ticket` is configured it returns `anonymous`, which `canRead` denies and the carrier refuses on every unary (blanket `forbidden`), stream (zero frames), download (403), and `/api/respond`. "Internal full access" is decided by the resolved principal — the in-process client's `{kind:'token'}` default (it never touches the HTTP fence) or an explicit full-token header — never by Host. Enforcement is at dispatch, not schema:
- *Unary* ([`handler.ts`](../../../packages/host/apiproxy/src/fetch/handler.ts)): before invoke, a full-token-only set (`session.setAccess`/`getAccess`) rejects tickets, and a session-scoped call (`sessionScopeOf` reads `sessionId`, else subagent `parentSessionId`) is refused `403 forbidden` unless `api.access.canRead`. `session.list`/`session.search` rows are filtered per ticket user after invoke; the `session.export`/`workspace.file` download GETs are gated by their `sessionId`.
- *Streams* ([`api-proxy.ts`](../../../packages/host/apiproxy/src/api-proxy.ts)): `muxSubscribers` carry a per-stream `subscribed` set and `canEmit` gate; every frame routes only to subscribers whose principal may read its session. A revoke is live (per-frame `canReadSession` re-check); a grant defers to the next reopen (a never-subscribed session emits nothing). The host stream filters per-session frames and suppresses workspace-level and forwarded (`host/remote-event`) frames for tickets.
- *Remote gateway* ([`rpc-host.ts`](../../../packages/client/connection/src/rpc-host.ts)): the Typert gateway serves session-scoped remote methods (`messageFeedback/list|put|delete` via `args.request.sessionId`, `commands/list` via `args.agentId`) through the connection interceptor, OFF the ApiProxy dispatch — a real bypass channel for authenticated ticket callers. The connection plugin installs a `RemoteAclGuard` on `HostConnectionService` that runs at the carrier BEFORE the gateway sees the call: full token bypasses; a ticket needs `canRead` on the call's session (extracted by the SAME `sessionScopeOf`, extended with `args.request.sessionId`/`args.agentId` arms); an anonymous caller, or a ticket call with no extractable session id while ticket auth is on, is refused with the `forbidden` envelope. The gateway itself stays unaware of tickets.
- Management `session.setAccess({sessionId,userIds})` / `session.getAccess({sessionId})` are new full-token-only RPC methods (a user cannot edit their own access); the read predicate and both methods live on a new optional `ApiProxy.access` facet, and a new `forbidden {sessionId?}` error code (200 + envelope) is distinct from the transport 401.

**Format-version verdict.** Per-session access is host authorization metadata, never model-visible content, so `model-visible ⟺ logged` does not require it in the session log, and placing it there would violate the complementary direction. It rides its own storage domain like the workspace registry; `SESSION_FORMAT_VERSION` is untouched.

**Opt-in wiring (web-app bundle).** Ticket auth and the ACL store are OFF by default and gated on a single env var, mirroring `DSH_API_TOKEN`: [`resolveWebTicketSecret`](../../../packages/bundle/web-app/src/ticket-secret.ts) reads `DSH_TICKET_SECRET` (validated ≥32, never generated/persisted — it must match Odoo's minter). When set, [`web-app`](../../../packages/bundle/web-app/src/index.ts) publishes `webRuntime.ticketSecret` (so `connection` derives `auth.ticket` via `deriveWebRuntimeAuth`) AND composes `SessionAccessService`. When unset, neither is configured: no ticket principals exist, the store is absent, and the standalone same-origin SPA keeps working token-less — byte-for-byte. The two arrive together on purpose: ticket auth turns on the absent-fail-closed rule that a token-less SPA could not satisfy without the ACL layer.

## Alternatives considered

**A maintained JWT library (jose HS256) instead of hand-rolled HMAC.** Rejected per "deps over hand-rolling": the ticket is a private credential between one Odoo minter and this verifier — no third-party JWT consumer — so jose's JWK/JWS/multi-alg generality deletes no owned code while adding a runtime dependency. The compact format carries NO `alg` field, so algorithm-confusion / `alg:none` is impossible by construction (the verifier only ever computes HMAC-SHA256) — strictly safer than JWT here. `verifyTicket` is the one seam a future jose swap would replace.

**Relaxing the browser-marker CSRF fence for tickets.** Rejected: the decided deployment is same-origin (nginx serves the SPA and the harness `/api` on one authority), so a browser-marked ticket request passes the existing fence naturally with the origin in `trustedHosts`. Relaxing a mitigation needs a forcing reason, and same-origin removes it; keeping the fence preserves cross-site replay protection for the ticket path too. A future different-origin deployment is a separate, deliberate CORS decision.

**Per-user access in the session log (a logged event + projection).** Rejected: the ACL is not model-visible, so logging it would inject non-model data into the model-visible reconstruction plane and force a `SESSION_FORMAT_VERSION` consideration. The separate storage domain gives the same durable/reconstructable posture without either cost.

**Allow-by-default (no record ⇒ visible) for tickets.** Rejected for fail-closed: a session with no access record is invisible to every ticket user; only the full-token management plane (Odoo/admin/loopback) sees it. Management `set` is the sole way a session becomes visible to a ticket user. `canRead` is written as allowlist membership so absence can never read as allow.

**Live grant mid-stream.** Deferred (not rejected): a revoke is security-critical and stays live through the per-frame gate; a mid-stream grant waits for the next stream reopen, since the real pattern is ~1 user / 1 session and the `onChanged` live re-baseline is complexity not yet paid. `onChanged` exists as the seam for that upgrade.

**Threading the principal through every `ApiProxy` method signature.** Rejected as unnecessary: the `ApiProxy` object is reached only through `toFetchHandler` and the WS downlinks, so gating unary in the carrier dispatch and streams in their generators covers every entry point. The principal rides beside `signal` (streams) or is applied in the carrier (unary), and method impls stay principal-free except the two management writes.

## Consequences

A browser carrying a per-user ticket now reaches the harness directly and sees only its granted sessions across unary calls, list results, downloads, and both event streams, filtered in the Node stream; Odoo mints/refreshes tickets and manages grants through the full-token management methods. Behavior is byte-for-byte unchanged when neither `auth.ticket` nor the `sessionAccess` seam is composed: no ticket principals exist, every path resolves to full-token, and the pre-existing apiproxy/connection suites pass untouched — no default bundle composes the ACL store yet (config wiring is a later step). `canReadSession` is fail-closed: a ticket with the ticket layer configured but no `sessionAccess` store composed resolves to no access. Nothing is model-visible and no session event is added, so no snapshot fixture or format-version bump.

**Known gaps (deliberate, flagged for follow-up).** `session.create` is not session-scoped, so a ticket may create a session but is not auto-granted access to it (fail-closed ⇒ invisible until Odoo mints access) — deliberate because Odoo owns session creation and granting; the SPA's "New Session" routes through Odoo (full token) which does `session.create` + `setAccess(creator)`, so no auto-grant is needed. `workspace.*` WRITE methods (`create`/`rename`/`delete`/`insertBefore`/`insertSessionBefore`/`archiveSession`) are now full-token-only in `FULL_TOKEN_ONLY` — a ticket is refused at dispatch, ahead of payload parsing, so registering a host directory or reorganizing the shared roster is management the Odoo/MTIL front owns; `workspace.list` and the `workspace.file` download stay reachable (the SPA reads the roster, and the download is gated by its own session id). The Chinese Agent Note counterpart and i18n sidecar are pending (bilingual is explicit-invocation only).

## Addendum (2026-08-22): ticket cookie transport and the MTIL gate

**Second credential transport: the `dsh_ticket` cookie.** A browser cannot set an `Authorization` header on a WebSocket handshake or a GET download, so a header-only ticket left the `events.mux`/`events.host` downlinks and the `session.export`/`workspace.file` downloads unauthenticated for the browser — the exact channels per-user filtering depends on. [`authenticateApiRequest`](../../../packages/client/connection/src/api-auth.ts) now also reads the ticket from an HttpOnly `dsh_ticket` cookie (`TICKET_COOKIE_NAME`), which the browser sends automatically on every same-origin `/api` request including the WS handshake. It is the single credential-extraction point, so the cookie flows unchanged into unary dispatch, the WS upgrade (`principalOf`), and the reachability fence. The `Authorization` header stays authoritative; the cookie is consulted only in its absence. A cookie value is verified ONLY as a ticket, never matched against the full API token, so an ambient cookie can never escalate to unscoped access. The browser-marker CSRF fence still applies (a cookie-bearing same-origin request passes on `Origin===Host`, not on the cookie), and `SameSite=Strict` on the cookie plus that fence close the CSRF that ambient cookies would otherwise invite.

**Minting and delivery (MTIL, Flask).** The pre-existing `get_config` endpoint is reserved for another purpose, so the gate is a new `POST /api/mtil/get_config_v2` (reference impl in [`apps/api.py`](../../../apps/api.py)). It reads the signed-in user from the MTIL session cookie and, on success, `Set-Cookie: dsh_ticket=<v1 ticket>; HttpOnly; Secure; SameSite=Strict; Path=/api` while returning only `datas.expires_at` in the body (the SPA never sees the ticket). The Python minter reproduces the `dsh-user-ticket` wire format byte-for-byte (verified: a Python-minted ticket resolves through `verifyTicket` and the cookie path). Same-origin deployment is required (nginx maps `/api/mtil/*` to MTIL and the rest of `/api` to the harness) or the cookie never reaches the harness; the `userId` MTIL signs MUST equal the id the ACL is keyed by.

**SPA gate.** The frontend (submodule) renders nothing but a connecting spinner until `get_config_v2` resolves: a 2xx `status:true` mounts the app, a 401/`status:false` shows a terminal "connection refused" screen, and no harness API is touched before it passes. Because the ticket rides an HttpOnly cookie the SPA cannot read, a background timer re-probes `get_config_v2` `expires_at`-minus-margin to have MTIL re-set the cookie; a refresh that comes back denied tears down to the denied screen.
